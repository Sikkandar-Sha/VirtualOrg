VirtualOrg

A synthetic enterprise for testing risk-posture products — with the answer key included.

The problem

You cannot test a posture engine without an enterprise, and every enterprise you can get is wrong

You are building something that reads a SIEM, an ITSM, a GRC platform and a scanner over their APIs, and produces residual risk per service, control effectiveness, and a board-level score. To know whether it works, you need somewhere to point it.

OptionWhy it fails
A real customerYou cannot. And even if you could, nobody knows what the right answer was — so you cannot tell a good posture from a plausible one.
A demo datasetClean, consistent, complete. It never exercises correlation, conflict or coverage gaps, which are the only hard parts.
Real products in a labMonths of work, no ARM64 images for several, and at the end you still have no ground truth.
The idea

Model the enterprise once. Make every tool a lossy lens over it.

Your product calls an endpoint and receives JSON. It cannot tell whether that JSON came from a real product or a database query. So the world is modelled once — completely and truthfully — and every vendor API is a deliberately imperfect view of it.

A VirtualOrg whose lenses are faithful and complete is a database with extra steps. The loss profiles are the test.

Quick start

Seven seconds from clone to a running enterprise

git clone https://github.com/Sikkandar-Sha/VirtualOrg.git && cd VirtualOrg
cp .env.example .env
docker compose up -d          # world, seven twins, Keycloak, Control Center
./scripts/status              # is everything running?
open http://localhost:3000    # the Control Center

Point your product at config/virtualorg/connectors.yaml — the whole environment switch is a config file, never a patched build. Then run python3 scripts/verify.py: 80 self-checks that prove the conditions the ground truth claims exist are genuinely observable through the vendor APIs.

Honesty

What this does not give you

With no vendor product in the loop, every claim of correctness rests on twin fidelity. Nothing here can tell you that a connector has misread a vendor's pagination — the connector and the twin would be wrong together, in green CI, indefinitely.

So every twin ships a provenance manifest recording where each response shape came from. All seven are marked unverified, because they were written from published behaviour rather than captured from a real tenant. Passing tests here show your product agrees with this environment — not that either agrees with the vendor. That gap is paid down by certification against real vendor tenants, not by hope.
