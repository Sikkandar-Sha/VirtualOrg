{# ============================================================ 1. OVERVIEW #} {% if chapter == 'overview' %}

One world, many lenses

An enterprise is not its tools. Every enterprise tool is a partial, lossy, opinionated view of one underlying organisation. VirtualOrg models the organisation once, completely and truthfully, in a single database, and every tool your kit connects to is a lens over it, with a scope, a loss profile, and an API shape.

{{ d.world_and_lenses(inventory, lens_rows, geom) }}
A word that trips everyone up

“Application” here means a business application belonging to the simulated company, “Nexus Sync 1”, “Edge Service 2”, not a running program and not a vendor tool. There are {{ inventory.applications }} of them and they are rows in world.application, part of the enterprise being modelled. The {{ lens_count_word }} boxes on the right are the only systems: vendor APIs your kit connects to. ServiceNow catalogues the applications the way a real CMDB does; it is not one.

This is the whole idea. If the lenses were faithful and complete, VirtualOrg would be a database with extra steps. The loss profiles are the test. Two lenses onto the same world, disagreeing, is what manufactures the correlation, conflict and coverage-gap problems your kit exists to solve.

Connect your kit in four steps

1 · Point the base URLs at the twin

VirtualOrg is only usable if your kit can be aimed at it without editing the kit. If you need a patched build to run against a twin, you are testing code that is not what ships. Everything below is config, never code.

Running fromBase URL
your IDE / hosthttp://localhost:8080/servicenow

2 · Authenticate

Static bearer token today. Every data endpoint requires it, including the /_lens/{id} and /_provenance metadata routes. A missing or wrong token is a 401. Four paths stay open: /healthz, because probes and CI need to know the service is up before they have anything to authenticate with, and it returns only liveness and the world seed; and /docs, /redoc and /openapi.json, which describe the interface and expose no data.

Authorization: Bearer {{ token }}

The examples below reference $VO_TOKEN rather than a literal value, because this page has no authentication and should not print a credential. Export it from your .env before pasting them:

export VO_TOKEN=$(sed -n 's/^VO_TOKENS=\([^ #,]*\).*/\1/p' .env)

Set VO_TOKENS in .env to change it. It is comma-separated, so several tokens can be valid at once.

Real OAuth is available. VO_AUTH_MODE=jwks validates RS256 tokens against Keycloak's published keys, signature, issuer, audience and expiry, nothing stubbed. Fetch one with the vo-kit client credentials against /realms/virtualorg/protocol/openid-connect/token. A static token is refused in that mode, and so is a tampered signature.

Binary evidence needs a second credential. Attachment metadata hands you a download_token; the content endpoint refuses a bearer token alone with a 403, and refuses anything over 5 MB with a 413. Real GRC platforms gate attachment bytes separately from the record API, so a connector that assumes one credential covers both will fail here.

Traps the environment sets deliberately

TrapWhy it bites
IPs are recycled The address pool is smaller than the asset count, so an IP is not a stable key. Matching on IP alone will merge two machines.
ServiceNow returns FQDN in both name and fqdn The short hostname is not recoverable from ServiceNow: it duplicates the FQDN into both fields. Tenable and CrowdStrike do carry it, so LT-4001 is findable, just not where a CMDB-first connector looks.
Splunk only knows assets that alerted Absence from the SIEM is not evidence a machine does not exist.
Staleness differs per lens A CMDB row up to 24h old and a SIEM row 5 minutes old are not equally authoritative, and the older one is old, not wrong.
Owner names are strings, not ids People appear as bare names on assets and controls. HR calls the same person WD-100001 and the IdP calls them mei.andersen1, three representations, no shared key. Two people can also share a name.
HR cannot see contractors The system of record covers employees only. A departed contractor has no HR record at all, so their leaver status is unconfirmable, and absence of a termination record is not evidence they are still employed.
The IdP no longer tells you who left terminationDate is written by the deprovisioning workflow, not by HR. When that workflow failed, which is exactly the orphaned-access case, the account is ACTIVE with no date. Finding it needs the HR join.
The EDR is the one join that works It names devices by agent id but also carries the short hostname, so it joins to the scanner without inference. Every other pair needs resolving.

How the kit gets scored

Because the kit writes nothing back, the whole system is a pure function: world-state → vendor responses → posture. Snapshot world W₁, record posture P₁; any change in posture without a change in the world is a regression.

Score your product

scripts/score reads what your product concluded and reports precision and recall per family, plus exactly which of the {{ "{:,}".format(corpus.reachable_traps) }} retrievable traps it fell for. {{ "{:,}".format(corpus.traps) }} are planted in all; the rest sit on records no API returns, so no kit can meet them.

python3 examples/reference-kit/kit.py > posture.json
./scripts/score posture.json

The contract is deliberately small. Findings match on the (family, subject_kind, subject_id) triple and never on claim text, so it measures whether the right thing was found rather than how it was phrased.

Emit whatever identifier the vendor API gave you. The scorer resolves C-017, lt-4069.corp.local, an agent uuid or a staff number back to the canonical entity, because that is the same entity-resolution problem your product already had to solve. It refuses to score a posture produced from a different world, because comparing answers to the wrong answer key is worse than not scoring.

Where the answer key lives

The scorer reads ground truth from the Control Center at /export/groundtruth, never from a twin. A kit that could fetch its own marking scheme would not be measuring anything, so the answer key is reachable only from the harness side of the boundary.

A worked example

examples/reference-kit/ is a small, readable consumer that produces a scoreable posture. It is deliberately naive: it attributes alerts to controls by matching words in the detection rule name against words in the control title, which is exactly the inference the traps exist to punish. Its score is what that approach is worth, and it is a useful floor to beat.

Scoring attribution

Nothing in any vendor API links a detection to a control, that inference is the kit's core job. world.evidence.control_id is the true answer for every event, and is_trap marks events linked to a control they do not evidence. A decoy is not inferable from topic alone: it exists to measure whether a system asserts a link it cannot support, rather than to reward a better classifier.

The real assertion

Ground truth is not just expected posture; it is expected lineage. A score of 68 must decompose into what made it 68 rather than 74, and each of those must decompose again to a specific detection or overdue finding. You can produce the right number for the wrong reasons, and that is worse than a wrong number, it survives scrutiny until someone drills into a driver, finds it does not hold up, and stops trusting the tool. Testing the number is easy. Testing the explanation is the job.
